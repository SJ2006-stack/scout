# Scout Android companion

The phone app for Scout. It opens `https://scout.shrianshjaiswal.me` in a WebView and adds native features the web page cannot do alone. It lives in `android/` of the `scout` repo (moved from the old `scout.apk` folder on Nov 8, 2026). `app/google-services.json` is ignored by git: download it from the Firebase console (project `scout-b4da3`, Android app `app.scout`) before building.

Current version: **0.9.7** (versionCode 21). Android 15 target (`targetSdk 35`), `minSdk 26`, Kotlin, Gradle. 0.9.7 adds the items and taps Place Order when you have decided to order from Blinkit, Zepto, or Instamart. It stops if a UPI PIN appears and does not type it. It still fills the app on screen while Scout is recording: name, email, phone, and details from the command. It taps Submit only when asked, and it does not tap Pay on a form. Sent to Firebase App Distribution on Nov 10, 2026, to shriyanshjaiswal.xf@gmail.com. Not yet tried from that update.

## What it does

- **WebView shell:** every build loads `https://scout.shrianshjaiswal.me/chat` (Azure `sj-scout`), so the app works without this Mac. It opens `/chat` because the main host serves the public landing page at `/` (fixed Nov 8, 2026, after 0.9.3; in 0.9.3 the app showed the landing page). The sign-in exchange reads every `Set-Cookie` header (`sessionFromSetCookies`), because Azure also sends `ARRAffinity` cookies, and reading only one dropped `scout_session` so the page stayed signed out. To test against a local server, add `app/src/debug/res/values/strings.xml` with `azure_origin` set to `http://127.0.0.1:8787` and run `adb reverse tcp:8787 tcp:8787`. Remove that file again before sending a build to testers.
- **Native bridges** exposed to the page:
  - `ScoutNative`: native features such as the microphone (`window.ScoutNative.request({ op: "microphone" })`). Ops: `location`, `microphone`, `camera`, `notification`, `biometric`, `share`, `qr`, `permissions`, `accessibility`, `action`, `sign_out`. The `permissions` op opens the in-app Permissions panel from Scout Settings. The `accessibility` op opens Android's Accessibility settings. It is in this tree and not in the Firebase 0.9.4 build; that build still opens the permissions panel, where Automation does the same thing. After phone, name, and the about step, the page stays on Turn on Accessibility until the service is on, and it comes back if the service is later turned off. A browser that is not the app skips that screen. `sign_out` (in this tree, not in 0.9.3) signs the app out and shows its Google sign-in screen; the page uses it for Sign out and for "Continue with Google", because a Google popup cannot open inside the WebView.
  - `action` runs a Scout phone action synchronously and returns `{op, id, status, message}` (`companion/PhoneActions.kt`): alarm and timer through the Clock app, reminders scheduled with `AlarmManager` and shown by `ReminderReceiver`, list and cancel reminders, open an allowlisted app (`PHONE_APPS`, mirrored in `<queries>`), maps, share, flashlight, volume, and capabilities. Expired or malformed actions are refused. `send_whatsapp` opens `https://wa.me/<number>?text=` with the package pinned to WhatsApp or WhatsApp Business. When the accessibility service is connected, that run adds WhatsApp to the service's package list (the list is otherwise only the shop and event apps, so WhatsApp opened and then nothing could be read or typed) and the phone taps Send. A name instead of a number searches and sends to the first chat with that name when several match. The search name is typed again if the keyboard moves the field. The empty-box microphone is not tapped. If the service is off, a number still opens with the text filled in and Send left for them. Opening an app, sharing, sending a WhatsApp message, and muting the ringer show an Allow dialog and report the outcome later as a `scout-native` event. `app_cart_add`, after Allow, adds Blinkit, Zepto, and Instamart items through an Accessibility service limited to the store and event packages. Instamart stops with `no_address` when the cart says "Add address to proceed" and does not open the address editor. Instamart sends the search link right after starting Swiggy rather than waiting for its home, and sends it again if a cold Swiggy lands on home (agent-measured Nov 6: 16.6 s cold, 12.9 s warm, was 25 s). Every cart result carries `elapsedMs`, the run time after Allow, which Scout uses for its timing estimates. A Shop basket sends every item for one store in a single `app_cart_add`, and each store's script adds them one after another in the same run; a multi-item run from the chat has not been tried on the phone yet. The debug build only (`app/src/debug/res/xml/network_security_config.xml`) allows plain http to `127.0.0.1` and `localhost`, so it can load a local server over `adb reverse tcp:8787 tcp:8787`. A normal tap still refuses pay, Place Order, proceed to pay, UPI PIN, CVV, Blinkit `cv_checkout_container`, and Zepto `cart-pay-button`. When the order was confirmed, after the cart is filled Scout taps that store's Place Order button and stops if a UPI PIN or code appears. It does not type the PIN. One run at a time. While Scout is driving another app, Take control and Stop sit on top of that app, and the same actions are on the notification. Take control pauses Scout so you can type and tap; Resume hands it back. Stop, a touch while Scout is driving, or leaving the app ends the run. A touch while you have control does not. This bar is in the local debug build installed on the connected phone on Nov 9, 2026. It is not in the Firebase 0.9.4 build, and a live run has not been tried since that install. `get_capabilities` reports `automation.serviceOn` and whether Blinkit, Zepto, Instamart, BookMyShow, District, and Luma are installed, with version. `app_event_book` opens a BookMyShow, District, or Luma listing with the package pinned, closes a recognised dining or membership sheet, and stops before checkout, pay, register, RSVP, or Book tickets. It does not pick seats. This debug build has not been installed on the phone and has not been tried live.
  - `open_checkout` (in this tree, not in the build testers have): Pay asks the app to bring that store or event app forward, or to open its cart link with `setPackage`. The user taps Place Order. Scout never taps Pay or Place Order. Instamart has no app-claimed cart link, so Pay only brings Swiggy forward. Blinkit uses `https://blinkit.com/cart`; a cold start launches the app because that link drops. This build has not been installed on the phone.
- **Voice:** the page's mic button uses the WebView microphone (`RECORD_AUDIO`). There is no live call button and no spoken-reply switch. Understand my screen uses a phone icon. The app records a clip with `MediaRecorder` (AAC, at most 30 seconds) and posts it to Scout's `/api/voice/stt`. Scout calls Gnani Prisma and returns text. The app does no speech recognition itself (`companion/Speech.kt`).
- **One-time codes:** `ScoutOtp` hands a code over with consent (`OtpConsent`).
- **Pay links:** `ScoutPay` opens pay links from Shop Scout (`PayLinks`).
- **Settings, Permissions panel:** shows the state of Microphone, Location, Camera, Notifications, and Automation (Accessibility). The Automation row opens Accessibility settings. Each other row can request that permission. A button opens the Android app-details settings for a permission the system will no longer ask for.
- **Sign-in and sync:** the app starts on Continue with Google. Firebase Auth stays signed in. The app posts that account's ID token to Scout `POST /api/auth/google`, stores the `scout_session` cookie for that person, and flushes it when the page finishes and when the app pauses. A new person then adds a phone number, a name, and the optional about-you step (city, home pincode, food, what they go out for, reply language) on the page inside the app. The page then stays on Turn on Accessibility until Scout's accessibility service is on. The same screen comes back if they turn it off later. The next launch opens the same account. Sign-out, or a different Google account, clears cookies and WebView storage before the next person is signed in. Profile sync still goes to Firestore (database `scout`, region `asia-south1`). The public site has `POST /api/auth/google` since the Nov 8, 2026 deploy. The Firebase tester build has it since 0.9.3.
- **Companion desk:** pairing (`PairCode`), task codes (`TaskCode`), and desk hosts (`DeskHosts`) connect the phone to the web chat.
- **Scout Drop (share to Scout, in 0.9.4, `drop/`):** Scout appears in the Android share sheet for text, links, and JPEG, PNG, or WebP images (`SEND`, and `SEND_MULTIPLE` for images). `MainActivity` is `singleTask`, so a share while Scout is open arrives through `onNewIntent` instead of a second WebView inside the sharing app.
  - **Checks:** `readShare` takes up to 20,000 characters of text with the subject or title, and up to 5 web links kept as written and never opened. It takes up to 4 images and accepts only `content://` URIs. `file://` paths and Scout's own providers are refused.
  - **Copying:** `DropImporter` copies each image into `cacheDir/scout-drop` on a background thread while the sender's read grant is valid. A copy is cut off at 4.5 MB, the `/api/ocr` limit, and kept only if its first bytes are a JPEG, PNG, or WebP; the declared type is not trusted. A missing grant, an unsupported file, or an oversized file skips that image with a note, and a share with nothing usable shows a toast. No storage or media permission is added.
  - **Inbox and accounts:** `DropInbox` (in `ScoutApp`) holds one pending share; a newer share replaces it. A share is tied to the Firebase uid signed in when it arrives. A share received while signed out goes to the next account that signs in. Another account signing in, Sign out, sending, Discard, or 30 minutes deletes it and its files. A small manifest keeps it across Activity recreation and process death, and the saved share key stops a recreated Activity from importing the same intent twice.
  - **Bridge:** the page pulls through three `ScoutNative` ops, allowed only on Scout hosts and only for the uid bound to the page. `drop_take` returns text, links, notes, and image ids (no paths). `drop_file {id, image}` returns one image as base64. `drop_done {id}` deletes the share. After an import, the app sends `{"op":"drop"}` as a `scout-native` event so an open page pulls again. Nothing is uploaded until the person taps Send on the page's review card.
- **Screen Intelligence (`screen/`, in 0.9.5):** Understand my screen asks Android for MediaProjection (app-window choice on Android 14+; the older full-display dialog on Android 10–13), then records a short clip of up to 6 frames until Stop. If a command was already given, Scout can carry it out from the latest moment. A confirmed grocery order taps Place Order after the cart is filled and stops at a UPI PIN. A booking still stops before payment. Text written on the screen is not a command. Android 13+ also needs notification permission so Stop can show. Apps that block screenshots (payments, passwords) come back black and are refused. Nothing is uploaded until Send for analysis. Ops: `screen_state`, `screen_start`, `screen_stop`, `screen_frame`, `screen_take`, `screen_file`, `screen_done`. On Android 14+ the shared window's size arrives through `onCapturedContentResize`, including after rotation. The virtual display and its ImageReader are rebuilt only when that size actually changes; the previous reader is closed after the display stops drawing to it. Tried on the connected phone on Nov 9, 2026, with a local debug build that is not the Firebase 0.9.4 testers have. See Known limits.
- **Messaging:** `ScoutMessaging` handles push notifications.
- **Store relay** (`relay/PhoneRelay.kt`): while the app is open, it holds a WebSocket to Scout's `/api/relay` using the WebView's `scout_session` cookie. Scout's browser on Azure sends Blinkit, Zepto, Instamart, BookMyShow, District, and Luma connections through it, so those sites see the phone's address. The phone opens only those hosts on port 443 and passes TLS bytes it cannot read. It stops when the app leaves the screen and reconnects with backoff.
- **Sign-in copies** (`relay/CopyStore.kt`): Scout sends a sealed copy of each verified store sign-in over the same socket. The phone cannot open them, adds its own Android Keystore encryption, and keeps them in `noBackupFilesDir/vault`. On connect it offers them back, so a sign-in survives the server losing its disk. Revokes from Scout delete the copy.

## Build and ship

```bash
cd scout/android
gradle assembleDebug                 # app/build/outputs/apk/debug/app-debug.apk
gradle testDebugUnitTest             # JVM unit tests
```

There is no `gradlew` script, only `gradle/wrapper/gradle-wrapper.properties`. Use Gradle 9.5 or open the folder in Android Studio.

Builds are shared through Firebase App Distribution (project `scout-b4da3`):

```bash
firebase appdistribution:distribute app/build/outputs/apk/debug/app-debug.apk \
  --app <FIREBASE_APP_ID> --project scout-b4da3
```

Bump `versionCode` and `versionName` in `app/build.gradle.kts` for every release. The landing page invite form adds a tester through the same service (`FIREBASE_DISTRIBUTION_*` in Scout's `.env`).

## Layout

```
app/src/main/java/app/scout/            MainActivity, bridges, pair and task codes
app/src/main/java/app/scout/companion/  Speech, OTP handoff, device access, desk, realtime feed
app/src/main/java/app/scout/data/       Local store, companion sync, messaging
app/src/main/java/app/scout/drop/       Scout Drop: share intake, image copy, pending inbox
app/src/test/java/app/scout/            Unit tests (pair code, task code, OTP consent, desk hosts, runtime)
firestore.rules, firebase.json          Firebase setup
```

Never commit `local.properties`, `app/google-services.json`, signing keys, or Firebase service keys.

## Known limits

- Debug builds only are shipped. There is no release signing or minify.
- Tests are JVM unit tests. There is no instrumented test for the permission flow.
